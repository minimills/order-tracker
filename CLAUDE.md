# Belfast Mini Mills – Order Tracker

Project spec. Read this at the start of every session.

Belfast Mini Mills (Prince Edward Island, Canada) builds fibre-processing machines and ships them worldwide. Orders are currently tracked in a Google Sheet; this web app replaces it. The user is the office manager (not a developer).

## STACK
- Frontend: Vite + React + TypeScript + Tailwind CSS, React Router (HashRouter, because it will be hosted on GitHub Pages), date-fns, a toast library (sonner).
- Backend: Supabase (Postgres database, Auth, Row Level Security, Edge Functions).
- Scheduled jobs: GitHub Actions cron running Node scripts (added in later phases).
- AI: swappable provider. One shared module used everywhere, chosen by AI_PROVIDER = gemini (Google AI Studio free tier, the default to start), claude (Anthropic API, Claude Haiku) or ollama (local), and AI_MODEL. Only ever called server-side (Edge Functions or GitHub Actions), never from the browser.
- Email: our HostGator cPanel mailbox, IMAP (port 993, SSL) to read, SMTP (port 465, SSL) to send. Credentials only in Supabase secrets and GitHub Actions secrets.
- Timezone: America/Halifax. Currency per order: CAD or USD.

## CORE CONCEPTS
- An ORDER belongs to a CUSTOMER and has many MACHINES. Each machine has a machine type and a unique serial number.
- Order numbers are sequential (next after the highest). A split shipment uses suffixes: 76-1, 76-2.
- Serial numbers = machine type code + "-" + 4-digit number, counted per machine type (e.g. LCR-2072 then LCR-2073). Must be unique; generated atomically in the database.
- Order STAGES: Quote, Confirmed, In production, Ready (built, being tested), Ready to ship, Shipped, Cancelled. Board stages (have a queue place and serials): Confirmed, In production, Ready, Ready to ship (`is_board_stage()` in SQL, `BOARD_STAGES` in `src/lib/types.ts`). The stored values never change; the names people see can be renamed in Admin → Stage names (`app_settings` key `stage_labels`, e.g. `{"Ready": "Ready / testing"}`). ALWAYS show stage names through `stageLabel()` / `useStageLabels()` from `src/lib/stages.ts`, never the raw value. Imports accept the stored value or the shown name; the backup export writes the stored value.
- QUEUE POSITION ("board number"): this is our shop board, which tells the shop which order to build next. Orders in Confirmed / In production / Ready to ship have a board number 1..N. Moving an order up or down renumbers every other board number. When an order is Shipped or Cancelled it leaves the board and everyone behind it moves up. Serial numbers follow board order: per machine type, lower board numbers get lower serials. When the board changes, serials of machines not yet built are reassigned to keep that order; machines marked built keep their serial forever.
- DISPLAY RULE (owner's request): the board number is never shown as a number in the app. Orders are always referred to by their Order #. `orders.board_position` still exists internally as the order of the shop queue (drag / ↑ ↓ on the board, serial order); describe it in words ("moves up the queue", "3rd in the queue" on the admin repair page only).
- Each order has: expected ship date, actual ship date (the day the shipment left), delay in days = actual - expected (negative = early), voltage (120V / 240V / Unknown), delivery equipment (Liftgate / No liftgate / Forklift / Tractor with forks / Unknown), freight type (LTL / FTL / LCL / 40' container / Other), free-text notes.
- PAYMENTS per order: order total, down payment (amount, due date, received date), balance (amount = total - down payment, due date, received date), plus optional extra payments. Show down payment as a % of total.
- ALERTS: payment due in 7 days, 3 days, today, overdue; expected ship date in 14 days / passed without an actual ship date; voltage Unknown on a confirmed order.
- Later phases: email sync, AI notes per order, an "ask the agent" chat, one-click reminder emails.

## ROLES, DROPDOWNS AND ARCHIVING (migration 0007 – follow these in every feature)
- ROLES (changed by 0018, see PERMISSIONS): `allowed_users.role` is `admin` (sees and does everything) or `staff` (shown as "User": sees and does ONLY what an admin allowed). There is always at least one admin (a trigger blocks removing the last one). Never use `useAuth().isAdmin` to show or hide things; use permissions.
- DROPDOWNS: never hard-code choice lists in the code. Load them from `option_lists` (`list_name`, `value`, `sort_order`, `archived`, `locked`), ordered by `sort_order`. Lists: `voltage`, `delivery_equipment`, `freight_type`, `payment_type`. Columns `orders.voltage`, `orders.delivery_equipment`, `orders.freight_type` and `payments.payment_type` store the option's text; a trigger rejects values not in the list. Dropdowns offer only non-archived values, but still show an archived value already saved on a record. Renaming an option updates every record using it. `locked` options (voltage/delivery "Unknown", payment "Down payment"/"Balance") are built in and cannot be renamed, archived or deleted. New dropdowns = new `list_name` rows plus a validation trigger.
- ARCHIVING: `orders`, `customers`, `order_machines`, `machine_types` and `option_lists` have `archived`, `archived_at`, `archived_by` (filled automatically). The app archives instead of deleting; delete is admin-only and rare. Normal screens filter `archived = false`; offer a "Show archived" toggle where useful. An archived order leaves the board like a cancelled one; an archived unbuilt machine gives its serial back.

## ADMIN AREA (migration 0012 – follow these in every feature)
- Everything a manager might want to change must be editable in the Admin area (/admin), never by a code change. New settings go in `app_settings` (admin-only write) with a page under /admin.
- /admin pages sit under `<Page permission="admin.<area>">` in `App.tsx` (full admins, or people given that admin page; the "Admin" menu item shows when any admin page is allowed), BUT the real protection is the database: admin functions start with `perform public.require_admin_area('<area>');`, admin tables use `can_admin('<area>')` RLS policies.
- Staff may not change, even through the API: board numbers, serial numbers, order numbers / split numbers (except the automatic 76 → 76-1), or an order's customer. The `aa_guard_admin_fields` trigger enforces this. The app's own board/serial routines call `lock_board()`, which sets `app.system_change` for that transaction so their updates pass the guard. Any new routine that changes board numbers or serials must call `lock_board()` first.
- Staff see only their own row in `allowed_users` and only order-related `activity_log` lines.
- Admin functions: `admin_board_change(order, position, apply)` (null order = Renumber all), `admin_set_serial(machine, serial)`, `admin_resequence_serials(type, start, apply)`, `admin_delete_record(table, id, 'DELETE')` (archived records only). `apply = false` previews (changes are rolled back). Each writes an `activity_log` line with action `admin` via `log_admin_action()`.
- Always show old → new (board numbers and serials) before saving a change that renumbers anything; reuse `components/admin/ChangeList`.
- Archive with a confirm box (`ArchiveDialog`); permanent delete only from Admin → Archive after typing DELETE.
- Company details for printouts: `app_settings` key `company` (name, address, phone, email, website, logo as a small PNG data URL). Read with `useCompany()`.

## CRATING (migration 0017 – follow these in every feature)
- `crates`: one row per physical crate, on an order. Sizes and weight are ALWAYS stored in metric (`length_cm`, `width_cm`, `height_cm`, `weight_kg`, 3 decimals so typed inches/pounds round-trip exactly), plus `plywood_sheets`, `build_hours`, `crated_on` (default today, Halifax), `crated_by` (free text, defaults in the app to the signed-in person's name), `notes`, archiving columns. Archived, never deleted, by staff.
- `crate_machines` (crate_id, machine_id): which machines are in a crate. A machine can need several crates; a crate can hold several machines of the SAME order ("This crate also holds…") so its weight and plywood are counted once. Save only through `save_crate(p_crate jsonb)` (insert or update + set machines, all-or-nothing, refuses machines from another order). "Not crated" = `uncrate_machine(machine)`: crates holding only that machine are archived, shared crates just drop it.
- Views: `machine_crating` (per non-archived machine: `crate_count`), `crate_report` (per non-archived crate on a non-archived order: order, customer, sizes, `machine_ids`, `machine_type_ids`, `machine_types` (one name per machine), `serials`).
- Units: `user_preferences.units` (`imperial` | `metric`, per person, `set_my_units()` rpc). In the app use `usePreferences()` (`src/lib/preferences.ts`, also cached in localStorage) and the helpers in `src/lib/units.ts` (`showLength`, `showWeight`, `showDims`, `lengthToCm`…). Display rounding: inches/cm 1 decimal, lb whole, kg 1 decimal. Never store imperial.
- UI: "Crated?" per machine on orders in Ready to ship / Shipped (and any order that already has crates) on the Order page and on the Shop board (`components/crating/MachineCrating`, `CrateDialog`, `UnitsSwitch`); "Crating summary" on the Order page with Copy (`CratingSummary`, text from `freightSummary()` in `src/lib/crates.ts`); `MoveDialog` warns (but allows) when marking Shipped with machines not crated; Crating report at /crating (`CratingReportPage`: groups crates by contents via `contentsLabel()`, avg / min / max, every crate, filters in the URL, two CSVs in the person's units).

Photos per item / per checklist: placeholders only (permission `checklist.photos`), to be built later.

- Scheduling settings: `app_settings` key `scheduling` (`working_days` ISO 1–7, `holidays` [{date, name}], `buffer_days`, `machines_in_parallel`), Admin → Scheduling (`SchedulingPage`, `admin.scheduling`). SQL helpers `scheduling_settings()`, `is_working_day()`, `working_days_between()`.

- Permissions: `orders.new.schedule`, `order.machines.crate_flag` (db), `schedule`, `schedule.machines`, `schedule.step_done` (db), `schedule.accept` (db), `orders.board.card.deadline`, `dashboard.list.schedule_changes`, `reports.department_delays` (+ `.by_month`, `.period`), `admin.order_defaults`, `admin.scheduling`.

## WORDING AND TONE (follow these in EVERY feature, even if a prompt says otherwise)
- Professional but plain business English: no jargon, no slang, no exclamation marks, no emojis. Title Case for page titles, section headings, menu items and buttons ("Save Changes", "Create Board"); sentence case for descriptions, hints, labels and messages.
- NEVER use the word "tick" (or "ticked", "unticked", "tick box") anywhere the user can see it, even if a prompt says "tick". Use instead:
  - Permissions: "Allow" / "Allowed", "Grant Access", "Revoke Access", "Not permitted".
  - Checklist items: "Mark Complete" / "Completed", "Mark Incomplete", "Not Applicable" (never "N/A" on screen).
  - Machine status: "Mark as Built" / "Built", "Mark as Crated" / "Crated", "Final check complete".
  - Settings and options: "Enable" / "Disable", "Enabled" / "Disabled".
  - Selecting items in lists or tables: "Select" / "Selected", "Select All", "Clear Selection", "Deselect".
  - Confirmations: "Confirm" and "Cancel" (never "OK" / "Yes" / "No").
- Actions: "Save Changes" (not "Save"), "Archive" when something is archived, "Permanently Delete" only when a record is really deleted, "Restore" (not "Bring back"), "Create" for new things ("Create Board"), "for example" (not "e.g."), specific nouns instead of "stuff / things / info".
- Messages: errors say calmly what happened and what to do next (never "Oops" / "Something went wrong"); empty states say what is missing ("No orders in this stage.", "No payments are outstanding.").
- ONE wording file: `src/lib/wording.ts` (`ACTION`, `STATUS`, `MESSAGE`, `confirmText`) holds the words for common actions, statuses and standard messages; use it in new screens and add to it rather than typing a common word again.
- Confirmation boxes: never `window.confirm` / `window.prompt` / `window.alert`. Use `confirmAction(message, { confirmLabel, danger })` and `askText(message, { initial, label, confirmLabel })` from `src/lib/confirm.ts` (drawn by `components/ConfirmHost`, mounted in `main.tsx`).
- Icons: simple single-colour line icons from `components/Icon.tsx` (`<Icon name="…" />`, add new shapes there), never emojis. Plain arrows (↑ ↓ ← →), × / ✕ for close and remove, ▸ ▾ for expand / collapse and ▲ ▼ for sorting are allowed.

## PERMISSIONS (migration 0018 – follow these in EVERY feature)
- RULE: every feature added in future MUST add its items (page, card, chart, list, column, field, tab, button, action) to the permissions catalog `src/lib/permissions/catalog.ts`, wrap every new screen element in `<Can permission="…">` (pages in `<Page permission="…">` in `App.tsx`, menu items in `src/lib/permissions/nav.ts`), and is hidden from non-admin users until the admin allows it in Admin → Users → Permissions (it shows a "New" badge there until reviewed). Sensitive data and every change must also be enforced in the database (RLS, secure views, or a `require_perm()` check in the function).
- Catalog item: `key` (dotted, e.g. `order.field.voltage`), `group` (menu group: Dashboard, Orders board, New order, Orders list, Order page, Payments, Crating, Reports, Agent, Settings, Admin), `section`, plain-English `label`, `levels` (`view` and/or `edit`; edit includes view), optional `requires` (usually its page), `needs` (data it shows, e.g. money columns need `payments`), `db` (also enforced by the database), `page` (a page switch: buttons/inputs on it need their own item).
- `npm run check:perms` (`scripts/check-permissions.mjs`) runs in the pre-commit hook (`.githooks`, set up by `npm install`), in `npm run build` and in the deploy workflow. It fails when a JSX element is not inside `<Can>`/`<Page>`, when a button/input/select/textarea is covered only by a page switch, when a key isn't in the catalog (code or migrations ≥ 0018), or when a catalog key is unused. Escape hatches, use sparingly: file header `// @permission-scope key, …` (a dialog/admin page only reachable through those keys), `/* @layout-helper */` (pure layout; its uses are checked), `/* @rendered-inside-can */` (e.g. table cell renderers drawn inside the column's `<Can>`), and the EXEMPT list in the script (sign-in, layout chrome, providers).
- App: `usePermissions()` (`src/lib/permissions/index.ts`: `can(key, level)`, `canAny`, `allowedBy(perms, key, level)` checks `requires`/`needs` too), `<Can permission | anyOf, level, fallback>`, `<Page>` ("You don't have access"), `HomeRedirect` (/ goes to the first allowed page in `START_PAGES`), `PermissionsProvider` (loads `my_permissions()`), menu built from `NAV_ITEMS`. Admins: everything. Don't load data a person can't see (e.g. skip `payment_overview` without `payments`).
- Database: `user_permissions` (user_email, `perms` jsonb `{key: 'view'|'edit'}`), `permission_templates`, `departments.default_permissions` (same shape = department preset), `app_settings` key `permissions_reviewed` (`{keys: []}` for the "New" badges). Functions: `has_perm(key, level)`, `has_any_perm`, `require_perm`, `require_any_perm`, `can_admin(area)` = `admin.<area>`, `require_admin_area`, `my_permissions()`, and (full admins only, each writes one `admin` activity line with added/removed/changed) `set_user_permissions(email, perms, source)`, `set_department_permissions`, `save_permission_template`. People given `admin.users` can add/remove users and departments but not change roles or permissions (`allowed_users_guard_role` trigger).
- Enforced by the database: `payments` (table RLS; `payment_overview` is a secure view returning nothing without it), `order.field.order_total` and `customer.contact` (column SELECT revoked on `orders.order_total`, `customers.emails`, `customers.phone`; read them only from the secure views `order_summary`, `payment_overview`, `customer_list`, which blank them without permission; NEVER `select *` from `orders` or `customers`, and grant SELECT on any new column added to those tables: `grant select (new_col) on public.orders to authenticated`), each order / machine / customer field edit (`check_field_permissions` trigger: column → key map; add new editable columns to it), `orders.new`, stage changes / shipping / queue moves (`check_board_change` in `apply_board_change`), `order.machines.*` (`change_order_machines`), `crating` (RLS + `save_crate`), activity (raw `activity_log` not readable; use the secure view `activity_feed`), and every Admin page (`can_admin('users' | 'departments' | 'machine_types' | 'dropdowns' | 'records' | 'serials' | 'board' | 'alerts' | 'company' | 'import' | 'archive' | 'activity')`). CSV exports are a screen control: a file only ever holds what the person can already read.
